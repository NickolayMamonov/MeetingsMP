# ИЗУЧИ ЭТО
**Незыблемые правила на протяжении всей задачи.**

## 1. Технологическая основа (факты)
* Kotlin 2.3, Compose Multiplatform, Gradle 8.14.3, JDK 21, AGP 8.11.2. Таргеты: Android, iOS, Desktop; web (wasmJs) — позже.
* Сеть: Ktor 3.4 + Ktorfit (KSP) в `meetings-sdk` (`api/`, `models/`, `auth/`, `MeetingsClient`). Новые эндпоинты — туда, по существующему стилю.
* State: мультиплатформенный ViewModel (`org.jetbrains.androidx.lifecycle`); сбор Flow — `collectAsStateWithLifecycle` (доступен в common).
* Design tokens: только из `core:uikit` (`MeetingsTheme`/`Colors`/`Typography`/`Shapes`). Цвета/типографику/отступы не хардкодить.
* DI: пока нет. Если план требует DI — Koin (KMP). Hilt в `commonMain` запрещён.
* Пакеты: `dev.whysoezzy.meetings` (UI/app), `dev.whysoezzy.meetingssdk` (SDK).

## 2. Качество кода
* **Идиоматичный Kotlin:** null-safety, корутины, Flow, `sealed`/`data`-классы.
* **Типобезопасность:** UI State — `data class`/`sealed interface`; Events/Effects — `sealed interface`.
* **Состояния экрана:** loading / content / empty / error обработаны явно.
* **Stateless UI + state hoisting**; декомпозиция на переиспользуемые компоненты.
* **Preview-driven:** для значимых composable — Compose `@Preview` (light/dark, ключевые состояния).
* **Lifecycle:** `viewModelScope`, `collectAsStateWithLifecycle`. Без `GlobalScope`.
* **Тестируемость:** логика покрывается `commonTest` без эмулятора; для UI — Roborazzi golden.

## 3. Что нельзя делать
* **НЕ** оставлять `TODO`-заглушки, пустые тела, «допишу позже» — только полные реализации всех затронутых файлов.
* **НЕ** оставлять закомментированный код и отладочный вывод.
* **НЕ** хардкодить строки/цвета/размеры и BASE_URL; никаких `localhost`/отладочных URL в проде.
* **НЕ** смешивать слои: UI не знает про Ktor/Ktorfit; Domain не знает про Compose/платформенные SDK.
* **НЕ** класть бизнес-логику в платформенные модули и не дублировать между ними.
* **НЕ** использовать Android-only в common: Hilt, `android.*`, `findViewById`, `AsyncTask`, `LiveData` (есть Flow).
* **НЕ** выходить за рамки плана; при архитектурной неоднозначности — остановиться и вынести вопрос, а не угадывать.
* **НЕ** мержить свой PR, пушить в `main`/`develop` напрямую, делать `git push --force`/`-f`.

# СДЕЛАЙ ЭТО

## ЭТАП 0. Подготовка
Сверь план с актуальным кодом. Если план противоречит фактическому состоянию репозитория или нарушает границы из `AGENTS.md` §2 — остановись и сообщи, не реализуй вслепую.

## ЭТАП 1. Итеративная реализация (порядок по умолчанию)
1. Domain (модели, контракты Repository, UseCase) → 2. Data (реализация Repository, DTO, mappers поверх `meetings-sdk`) → 3. UI State/Events/Effects → 4. ViewModel → 5. Composable (от атомов к экрану) → 6. Preview и edge cases → 7. DI-биндинги (если применимо).

**Процесс для КАЖДОГО шага плана:**
1. **Структурный чеклист:** выпиши полный список файлов шага и проверь модуль/пакет для каждого (§2).
2. **Сообщи, что реализуешь** и его место в архитектуре.
3. **Выдай/внеси полный код** идиоматичным Kotlin; комментарии — где логика неочевидна.
4. **Внутренняя петля (отладка):** при необходимости проверь поведение на таргете через MCP-инструмент `mobile` (рендер, `get_ui`, тап/ввод, logcat, `assert_*`). Для стабильности: `wait_for_element` вместо пауз, отключённые анимации, фиксированный locale, засеянное состояние. Это **вспомогательный** сигнал, не доказательство готовности.
5. В интерактивном режиме после файла спроси: «Корректировки или продолжаю?». В автономном — продолжай, но останавливайся на любой архитектурной неоднозначности или отклонении от плана.
