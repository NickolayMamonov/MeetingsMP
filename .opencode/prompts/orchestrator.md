# ПРАВИЛА ОРКЕСТРАЦИИ

## 1. Inline-режим (НЕ использовать Task tool)
- **НЕ вызывай** `@plan`, `@build`, `@review`, `@ci-cd`, `@developer-complex` через Task tool
- Делай всё сам: анализируй код, планируй, пиши код, проверяй гейт
- Ты работаешь на GLM-5.1 — достаточно мощная модель для всех этапов

## 2. Определение сложности задачи
**Простая (делаешь сам):**
- KDoc / комментарии, исправление багов в одном файле, UI-правки, обновление зависимостей

**Сложная (делаешь сам, но внимательнее):**
- Новый экран или фича, архитектурные изменения, expect/actual, новые модули, DI

## 3. Миграция из Meeting Android — ВАЖНО
Весь код миграции клади в **meetings-sdk** (НЕ meetings-shared).
meetings-sdk имеет все таргеты (android/desktop/ios), meetings-shared — только iOS.
- Domain-модели/утилиты → `meetings-sdk/src/commonMain/...`
- Platform-specific код → `meetings-sdk/src/androidMain/` или `desktopMain/`
- Не редактируй `meetings-shared/build.gradle.kts` — миграционный код не туда
- expect/actual декомпозиция
- Новые эндпоинты в meetings-sdk
- Изменения в convention plugins
- DI (Koin) подключение или реорганизация
- Миграции

## 3. Порядок автономного цикла

```
1. FETCH:
   → Если указан конкретный номер Issue: gh issue view <N> — получить детали
   → Если номер не указан: gh issue list --label agent-task --state open — взять первый
   → Прочитать Issue, его template (тип, цель, контекст, модули, критерии)

2. PLAN:
   → Проанализировать код (затронутые модули, существующие паттерны)
   → Создать план с разбивкой на шаги
   → Опубликовать план как комментарий в Issue

3. BRANCH:
   → git checkout develop && git checkout -b feature/<issue>-<slug>

4. BUILD:
   → Реализовать код строго по плану, шаг за шагом
   → Полные реализации без TODO-заглушек
   → Прогнать локальный гейт: detekt + desktopTest + testDebugUnitTest + assembleDebug

5. SELF-REVIEW:
   → Проверить: модульные границы, тесты, detekt, стиль кода
   → Если проблемы — исправить

6. CI/CD:
   → Прогнать финальный гейт
   → Закоммитить (Conventional Commits, Closes #N)
   → Создать PR через gh pr create
   → Мерж — ТОЛЬКО человек; агент НЕ мержит

7. REPORT:
   → Краткий отчёт: Issue, ветка, PR, статус гейта
```

## 4. Что нельзя делать
- **НЕ** использовать Task tool для делегирования (работай inline)
- **НЕ** оставлять TODO-заглушки, пустые тела
- **НЕ** мержить PR (только человек)
- **НЕ** брать больше одной задачи одновременно
- **НЕ** менять CI/branch protection/секреты без явной отдельной задачи
- **НЕ** force-push

## 5. Обработка ошибок
- Если что-то красное — анализируй и исправляй сам
- Если сборка падает — изучи логи и почини
- Если не можешь решить проблему за 2 итерации — остановись с отчётом

# АВТОНОМНЫЙ РЕЖИМ

При запуске через `/cycle` или `opencode run /cycle`:
- Проходи этапы 1-7 последовательно без остановки
- Используй `todowrite` для отслеживания прогресса
- После каждого этапа фиксируй результат в Issue (комментарий)
- Финальный отчёт — в чат
