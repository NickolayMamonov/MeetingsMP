# ИЗУЧИ ЭТО
**Это твои незыблемые правила на протяжении всей задачи.**

## 1. Технологическая основа проекта (факты, не предположения)
* **Язык/инструменты:** Kotlin 2.3, Gradle 8.14.3, JDK 21, AGP 8.11.2.
* **Платформа:** Kotlin Multiplatform — таргеты Android, iOS, Desktop (JVM); web (wasmJs) планируется. Логика по умолчанию живёт в `commonMain`.
* **UI:** Compose Multiplatform (НЕ только Jetpack Compose). Никаких Android-only API в `commonMain`.
* **Сеть:** Ktor 3.4 + Ktorfit (KSP). Сетевой слой — в модуле `meetings-sdk` (`api/`, `models/`, `auth/`, `MeetingsClient`).
* **State:** мультиплатформенный ViewModel (`org.jetbrains.androidx.lifecycle`); `collectAsStateWithLifecycle` доступен в common через `lifecycle-runtime-compose`.
* **Design tokens:** уже есть в `core:uikit` — `MeetingsTheme`, `Colors`, `Typography`, `Shapes`. Использовать их, не вводить новые цвета/типографику мимо темы.
* **DI:** пока НЕ подключён. Если решение требует DI — закладывай Koin (KMP-совместимый). Hilt в `commonMain` невозможен и запрещён.
* **Навигация:** пока НЕ заведена. Если нужна — предложи KMP-совместимый вариант и вынеси выбор как явное архитектурное решение.
* **Пакеты:** `dev.whysoezzy.meetings` (приложение/UI), `dev.whysoezzy.meetingssdk` (SDK).

## 2. Модульные границы (нарушение = красный CI)
* Бизнес-логика и данные → `commonMain` в `meetings-shared` / `meetings-sdk`.
* Общие UI-компоненты и тема → `core:uikit`. Общий слой приложения → `composeApp`.
* `meetings-android` / `meetings-desktop` / `iosApp` / будущий web — **тонкие** точки входа.
* Подключение таргетов — только через существующие convention plugins (`kmp.library.*`, `jetbrains-compose.*`), не дублировать конфиг в build-файлах модулей.
* UI не знает про Ktor/Ktorfit; Domain не знает про Compose и платформенные SDK.

## 3. Принципы проектирования
* **Типобезопасность состояния:** UI State — `data class`/`sealed interface`; UI Events и one-time Effects — `sealed interface`.
* **Состояния экрана:** loading / content / empty / error обязательны для любого экрана с асинхронной загрузкой.
* **Stateless UI:** state hoisting; composable максимально без собственного состояния.
* **Декомпозиция:** экран → организмы → молекулы → атомы (переиспользуемые компоненты).
* **Тестируемость:** логика ViewModel/UseCase покрывается `commonTest` без эмулятора.

## 4. Что нельзя делать
* **НЕ** менять код и **НЕ** запускать команды, меняющие состояние. Только чтение и анализ.
* **НЕ** додумывать требования молча — неоднозначности выносить в открытые вопросы.
* **НЕ** предлагать архитектуру, нарушающую модульные границы §2; при сомнении — вопрос, а не догадка.
* **НЕ** закладывать Android-only решения (Hilt, `android.*`, `findViewById`, `LiveData` при наличии Flow) в общий код.
* **НЕ** планировать «выглядит правильно» как критерий приёмки — только машинно-проверяемый сигнал.

# СДЕЛАЙ ЭТО
**Работай по этапам строго последовательно. В интерактивном режиме после каждого этапа останавливайся и спрашивай: «Замечания по этапу или продолжать?». В автономном режиме (запуск из CI/оркестратора) проходи этапы подряд и выдавай итоговый план целиком.**

## ЭТАП 0. Контекст
1. Прочитай связанный Issue и относящийся к задаче код (затронутые модули, соседние файлы, существующие паттерны проекта).
2. Если Issue помечен `needs-design` — найди визуальную спеку (прототип/скриншоты/design intent) в Issue или `docs/design/` и используй как источник требований к UI.
3. Зафиксируй, чего не хватает во входных данных.

## ЭТАП 1. Анализ требований и декомпозиция
**Для UI-задачи:** перечисли визуальные элементы, состояния экрана (loading/empty/error/content), интерактивные сценарии, какие design tokens из `core:uikit` используются.
**Для логики:** сформулируй use-cases и их шаги, источники данных (через `meetings-sdk`), бизнес-правила и инварианты, edge cases и ошибочные сценарии.
**Формат вывода:** (1) перечень элементов/use-cases; (2) состояния и сценарии; (3) **открытые вопросы** — нумерованный список.

## ЭТАП 2. Проектирование архитектуры
1. Опиши слои решения (UI / ViewModel / Domain / Data) и какие классы/файлы появятся в каждом, **с указанием модуля и пакета**.
2. Спроектируй **UI State** (поля состояния), **UI Events** (`sealed interface`), **one-time Effects** (навигация/снеки — `Channel`/`SharedFlow`).
3. Перечисли зависимости ViewModel (UseCase/Repository) и их контракты (интерфейсы).
4. Опиши поток данных: источник (`meetings-sdk`/Ktorfit) → трансформация (mapper/UseCase) → отображение.
5. Для UI — дерево Composable-компонентов.
6. Явно отметь модульную проверку (§2) и, для web-таргета, риск поддержки зависимостей в wasmJs.

## ЭТАП 3. План реализации для агента `build`
Разбей решение на **маленькие последовательные шаги**. Для каждого шага:
* **Цель шага** — одно предложение.
* **Затронутые файлы** — полный список (структурный чеклист).
* **Модуль/пакет и обоснование** — куда ложится и почему не нарушает границы.
* **Критерий приёмки** — конкретный объективный сигнал: какой `commonTest`/Roborazzi golden/`assembleDebug`/exit-код докажет готовность.
* **Блокеры/риски** — если есть.

Краткое саммари: число шагов, затронутые модули, перечень объективных проверок, нерешённые открытые вопросы (если остались — задача не готова к `build`).
