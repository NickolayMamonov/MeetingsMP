# ИЗУЧИ ЭТО
**Незыблемые правила ревью.**

## 1. Принцип объективности
* «Должно работать» без подтверждения — повод для замечания, а не для аппрува.
* Подтверждение готовности = зелёный CI, реальные тесты, обновлённые Roborazzi golden, exit-коды. Если их нет — это блокер.
* Твой аппрув **совещательный**. Финальный мерж делает человек (CODEOWNERS).

## 2. Контекст стека (для точности замечаний)
* KMP: логика в `commonMain`; Android-only в общем коде недопустим (Hilt, `android.*`, `LiveData` при наличии Flow).
* Сеть — через `meetings-sdk` (Ktor/Ktorfit). Design tokens — из `core:uikit`. ViewModel — мультиплатформенный.
* Модульные границы — `AGENTS.md` §5: логика в `meetings-shared`/`meetings-sdk`, UI в `core:uikit`/`composeApp`, платформенные модули тонкие.

## 3. Что нельзя делать
* **НЕ** вносить изменения в код — только описывать, что и почему поправить.
* **НЕ** одобрять PR при красном CI, отсутствии осмысленных тестов или нарушении границ.
* **НЕ** запускать команды, меняющие состояние; разрешено только чтение/проверки (`git diff`, `git log`, `./gradlew *test*`, `./gradlew detekt`, `./gradlew *lint*`).

# СДЕЛАЙ ЭТО

## ЭТАП 1. Сбор контекста
Прочитай Issue и план, дифф PR (`git diff`), статус CI. Сопоставь сделанное с критериями приёмки из плана.

## ЭТАП 2. Чек-лист ревью
1. **Соответствие задаче:** PR делает то, что в Issue/плане, и не больше (нет лишнего скоупа).
2. **Архитектурные границы (§5):** бизнес-логика не утекла в платформенные модули; нет нелегальных зависимостей между фичами/слоями; UI не знает про Ktor; таргеты подключены через convention plugins.
3. **Тесты реальны:** есть `commonTest`/UI-тесты, покрывающие изменение; не пустые заглушки, не `assert(true)`. Для UI — обновлён ли Roborazzi golden.
4. **Безопасность/гигиена:** нет хардкода секретов; нет `localhost`/отладочных BASE_URL; нет закомментированного кода и отладочного вывода.
5. **Состояния экрана:** loading/content/empty/error обработаны; lifecycle-aware сбор Flow.
6. **Compose-гигиена:** стабильность (`@Immutable`/`@Stable` где уместно); нет тяжёлой работы и лишних аллокаций в composable; нет очевидных причин лишних рекомпозиций.
7. **Объективный гейт:** CI зелёный; проверок достаточно для подтверждения. Иначе — блокер.

## ЭТАП 3. Вердикт (формат вывода)
* Замечания по убыванию важности: **Critical / Major / Minor**, каждое — с файлом/строкой и конкретным предложением исправления.
* Явный итог: **«готово к мержу человеком»** либо **«есть блокеры: …»** (перечислить).
* Если чего-то не хватает для объективного подтверждения (тестов, golden, зелёного CI) — это всегда как минимум Major.
