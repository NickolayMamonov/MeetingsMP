# ONBOARDING — запуск агентной разработки MeetingsMP с нуля

Пошаговый план для того, кто раньше не работал с агентами. Принцип: **ползком → шагом → бегом.**
Не строить всё сразу — сначала почувствовать одного агента, потом наслаивать.

Связанные документы: `docs/plans/2026-06-02-meetingsmp-agentic-system-design.md` (архитектура системы),
`docs/plans/2026-06-02-github-setup.md` (защита веток), `AGENTS.md` (правила агентов), `opencode.json` (конфиг).

Отдельного проекта нет: конфиги (`opencode.json`, `AGENTS.md`, `.opencode/`, `.github/`) лежат внутри
MeetingsMP. Отдельно ставятся только инструменты: opencode, claude-in-mobile, позже OpenClaw.

---

## Этап 0 — Понять модель работы (без установки)

Сессия агента — это цикл: ты даёшь задачу → агент читает файлы → предлагает/вносит правки и запускает
команды → **ты подтверждаешь каждое действие**. Два основных агента: `plan` (только смотрит/планирует) и
`build` (пишет код), переключение — **Tab**, вызов сабагента — через **@** (`@review`).
Права на действие: `ask` / `allow` / `deny`.

## Этап 1 — Соло-знакомство (только opencode, без нашей системы)

Цель — комфорт, не результат.
1. Поставить opencode: `curl -fsSL https://opencode.ai/install | bash`, проверить `opencode --version`.
2. Подключить подписку Go: `/connect` → OpenCode Go → вставить Go-ключ. Затем `/models` — посмотреть
   точные ID и префикс (`opencode/...` или `opencode-go/...`).
3. Открыть копию MeetingsMP, запустить `opencode`, остаться в режиме **plan**, попросить:
   «объясни, что делает модуль `meetings-sdk`». Посмотреть, как агент читает код.
4. Создать ветку-помойку, переключиться в `build`, дать тривиальную задачу (KDoc, переименование),
   подтверждать каждый шаг руками. Удалить ветку.

## Этап 2 — Подключить нашу конфигурацию

1. Положить в корень: `opencode.json`, `AGENTS.md`, папку `.opencode/prompts/` (plan/build/review).
2. Ключи: всё через подписку Go (`/connect` → OpenCode Go → Go-ключ). GLM и DeepSeek входят в Go,
   отдельных ключей не нужно.
3. Проверить, что префикс моделей Go в `opencode.json` совпадает с тем, что показал `/models`
   (при необходимости поправить три строки `model`).
4. Tab между `plan`/`build`, `@review` — убедиться, что все три модели отвечают.

## Этап 3 — Поставить клетку (CI-гейт) ДО автономии

По документу `docs/plans/2026-06-02-github-setup.md`:
1. Завести `develop`, сделать веткой по умолчанию.
2. Влить `.github/workflows/quality-checks.yml` и `.github/CODEOWNERS`, дождаться первого прогона.
3. Включить rulesets/branch protection: PR обязателен, нужен зелёный `Build & Unit Tests (blocking)`
   и аппрув CODEOWNERS, force-push и удаление запрещены, bypass пустой.

**Критерий:** прямой push в `develop`/`main` отклоняется; смержить без зелёного CI и аппрува нельзя.

## Этап 4 — Первая реальная задача целиком (изоляция через worktree)

1. Освоить `git worktree` — одна задача = один worktree = одна ветка.
2. **Первая задача (безопасная, инфраструктурная):** «подключить detekt в convention plugins».
   Прогнать через полный цикл — это заодно проверит весь контур на нерискованной задаче:
   - завести Issue → `plan` спроектировал → `build` в worktree реализовал → открыл PR →
     `@review` проверил → CI прогнал → **ты смержил**.
3. После detekt — перевести job `Static Analysis` в блокирующие (убрать `continue-on-error`, добавить
   чек в required). Затем — подключить Roborazzi той же схемой.
4. Повторить на 2–3 небольших задачах, пока цикл не станет привычным.

## Этап 5 — Глаза и руки (claude-in-mobile)

Когда Этап 4 стал рутиной: поставить CLI claude-in-mobile, поднять Android-эмулятор, сверить команду
запуска MCP в `opencode.json` (блок `mcp.mobile`) с README инструмента, проверить, что `build` видит
экран и читает logcat. Использует только агент `build`.

## Этап 6 — Пульт (OpenClaw) — отдельный сервис

Поднять gateway **строго за приватным периметром** (за своим VPN), не публиковать в интернет
(была RCE-уязвимость; беречься). Подключить Telegram, нацелить на репозиторий и opencode
(модели — те же через Go, отдельные ключи не нужны).

## Этап 7 — Рой и web

Запускать несколько `build`-агентов параллельно на разных Issue (помнить про 5-часовые лимиты Go
для GLM при тяжёлой нагрузке; DeepSeek V4 Flash почти не упирается). Отдельной фазой — web-таргет:
web-конвенции (`kmp.library.web`, `jetbrains-compose.web`) → wasmJs → аудит поддержки зависимостей.

## Базовые правила новичка (на весь путь)

- Любую задачу начинать в `plan`.
- Держать права на `ask`, пока не доверяешь потоку; потом ослаблять до `allow`.
- Первые запуски досматривать целиком. Агент будет ошибаться — для этого и есть гейт.
- Деньги: всё на flat-подписке Go; build/тесты — на дешёвой Flash, plan/review — на более сильных
  (GLM-5.1 / DeepSeek V4 Pro). Отдельной поминутной оплаты нет.
- Одна задача за раз, пока не освоишься; рой — потом.
- Этот чат-ассистент не часть рантайма: в работающем пайплайне кодит автономный `build`-агент opencode.
